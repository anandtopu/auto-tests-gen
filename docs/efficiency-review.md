# Efficiency review — skills, agentic workflows, caching, reuse

**Scope.** A requested review of the platform for opportunities to apply
skills, agentic workflows, loop engineering, graph engineering, prompt caching
and similar techniques — to improve performance, reduce cost, increase reuse
and maximize operational efficiency.

**Method, stated up front.** Most of these techniques are *already implemented
here*, several with measurements attached. So this review's first job is an
honest inventory — separating "implemented and measured" from "implemented but
unmeasurable today" from "genuine gap" — and its second job is to close the
highest-value gap that survives that sorting. A review that re-proposes what
exists would be padding; one that proposes what measurement contradicts would
be worse.

Verdicts used below: **HELD** (implemented, evidence attached), **UNMEASURED**
(implemented; the measurement is blocked and the blocker is named), **CLOSED
HERE** (gap found by this review, fixed in this change), **DEFERRED** (real
opportunity, deliberately not built, with a written trigger).

---

## 1. Skills — HELD

Nine skills under `.agents/skills/`: two *path-triggered* convention skills
(`e2e-api-conventions`, `e2e-ui-conventions`) whose `paths:` globs are DERIVED
from each test repo's layer+layout and regenerated by `make skills` — never
hand-edited, so conventions stay single-sourced — plus seven hand-authored
task skills (ai-qe, pr-review, test-generation, test-review, test-coverage,
test-data-generation, test-plan) launchable as named OpenHands agent
conversations. Two bundle a read-only `scripts/` context dump so the agent
gets one deterministic snapshot instead of improvising queries; a pin keeps
those scripts read-only.

Remaining opportunity: none structural. Skills coverage follows the estate's
QE jobs; new jobs get new skills as they appear.

## 2. Agentic workflows — HELD

Three deliberate multi-agent structures, each with a containment argument:

* **Generate fan-out** — one agent per resolved test repo, each confined to
  its own repo with its own conventions and catalog slice; a per-repo failure
  is contained (`fanout.skipped`) rather than failing the run.
* **Adversary/arbiter pair** — a read-only opponent hunts for what the plan
  author missed; the arbiter may only ADD scenarios. Runs before human
  approval, so it changes what the reviewer sees, never whether they are
  asked. Keeping the adversary's tools read-only is what stops it becoming a
  second author with the first author's blind spots.
* **OpenHands delegation** — a phase or a whole authoring job as a sandboxed
  conversation, completion-class by design (its files cannot reach the gate's
  checkout, so the harness materializes artifacts from its final message).

Remaining opportunity: none that survives the constitution. E.g. letting the
adversary edit the plan directly would be "more agentic" and strictly worse.

## 3. Prompt caching — HELD at the prompt shape, UNMEASURED at the provider

The prefix discipline exists everywhere it matters:

* `run_phase.sh` sends the prompt template VERBATIM and appends the
  run-parameters block LAST — substituting `{{KEY}}` inline used to plant a
  run-unique value in the first few hundred tokens and made every prefix
  uncacheable.
* `agent_context.py` orders context most-stable-first (protocol → estate →
  plan state → ticket → requester note) for the same reason, with a comment
  forbidding timestamps above the ticket block.
* The completion-provider prompt addendum lands INSIDE the run-parameters
  block, so prompts stay provider-agnostic without breaking the prefix.

What is NOT known: whether the provider cache actually engages on this shape.
`make cache-probe` exists precisely to measure it (two real triage runs
back-to-back; the second run's cache_read share is the verdict) and **refuses
mock mode with exit 2 — "Nothing was measured."** It is blocked on the same
CLI auth as every parity item (REVIEW.md item 5). Until that clears, the
honest statement is: the shape is cache-friendly by construction, the hit rate
is unmeasured, and `budgets.min_cache_hit_rate` will flag it per phase the day
real numbers flow.

## 4. Result reuse (the cache that skips the model entirely) — HELD

* **Phase cache** (`phase_cache.py`) — content-addressed on
  sha256(phase, PROVIDER:MODEL, prompt template, every context file's bytes):
  a stale hit is impossible, so there is no TTL. `generate`/`validate` are
  excluded BY CONSTRUCTION (their product is files + git state the gate
  inspects; replaying a contract would hand the gate a green report for work
  that never happened). Note: the cache shows 0 entries on this estate —
  correct, not broken. Mock mode bypasses `run_phase.sh` entirely, and all
  runs here are mock; the cache only populates on real-LLM runs.
* **Semantic plan reuse** (`plan_reuse.py`) — a ticket ≥0.80 similar to a
  HUMAN-APPROVED prior plan skips the testplan LLM phase; the adaptation is
  deterministic text surgery, the adversary still challenges it, and it can
  never auto-approve. Held behind `AIQE_PLAN_REUSE=0` until the quality eval —
  which is the right order: reuse before quality evidence would be saving
  money by shipping unmeasured plans.
* **Spec savings** (`spec_savings.py`) — counts approved scenarios a cataloged
  test already covers; refuses to price them in dollars (`usd: None`,
  `unmeasured`) because the measured medians do not exist yet.

## 5. Loop engineering — HELD

The loops that exist are bounded and their bounds are recorded: the
validate-repair loop (repair count lands in the run record and the scorecard),
the context-retry loop (exactly ONE retry with the full estate on
`missing_context`, recorded as `context_retries`), and — added two loops ago —
the retry rate limiter (3 attempts / 60m window / 60s cooldown, refusals
naming the limit and the wait). The pattern worth naming: every loop here has
a counter someone can read afterwards, which is what separates loop
engineering from retrying until it works.

## 6. Graph engineering — HELD in substance, not in name

The estate IS a graph and the platform routes on its edges: change →
`covers:` edge → test repo (with contract fan-out to consumers as a second
edge type); catalog evidence edges (`contract_match`, `route_match`) attribute
tests to repos; the trace matrix walks ticket → scenario → spec → gate commit
→ CI health end to end. Retrieval is hybrid: deterministic token overlap plus
a semantic vector index (SQLite float32 + pure-python cosine, per the
embeddings ADR), with TF-IDF fallback when embeddings are unconfigured.

A dedicated graph database would add operational surface without adding an
edge type the registry + catalog do not already express. DEFERRED, trigger:
a routing question that requires multi-hop traversal the current
resolve-then-fan-out cannot answer.

## 7. Interpreter-start overhead — the measured tax, one gap CLOSED HERE

The one genuinely new finding of this review. Profiling a mock run:
**61 python3 invocations, 24.4s of a ~27s run spent inside them**, of which
roughly 200ms per invocation is fixed interpreter start on Windows. Two
consolidations of the same duplicated-work shape have now landed:

* `spec_exemplars` 1+N invocations → one `all` pass (previous loop; component
  3306→1396ms, whole run ~2s by interleaved A/B, output byte-identical and
  pinned as bytes).
* **This review:** the jira branch parsed `out/ticket.json` FIVE times in five
  separate interpreters (components, labels, linked repos, fix versions,
  issue type). `engine/lib/ticket_fields.py` now reads it once and emits all
  five as shlex-quoted shell assignments — quoted because ticket text is
  untrusted JIRA data and the values are now `eval`ed (same precedent as
  `app_paths --sh`); verified byte-identical through real bash eval including
  an injection attempt and an embedded newline. Measured honestly: interleaved
  A/B on the whole jira run gave +505/−406/+1307 ms — **inside the noise** of a
  ~35s run, so no whole-run speedup is claimed. The justification is the
  removed duplicated work (four fewer ~200ms interpreter starts, bounded
  ~800ms) and one parse instead of five of the same untrusted document, with
  output pinned byte-identical.

The remaining ~40 invocations are individually justified (budget guard must
run BEFORE each phase; event emits are best-effort singletons) or structural.
The structural fix — a single resident Python process running the whole phase
chain — is DEFERRED: it would rewrite the pipeline's process model to save
seconds on a mock run whose real-LLM equivalent is dominated by model latency,
and the bash pipeline's per-step isolation is load-bearing for the gate's
trust argument. Trigger: real-run telemetry showing orchestration overhead
material next to model time.

## 8. Operational efficiency — HELD, with the spend controls as the ceiling

Budget envelopes per workflow, wall-clock + cost guard before every phase
(exit 77 aborts before the gate), the degradation ladder (60% → cheap tier for
non-judgement phases, 80% → halved context budgets, 100% → abort; judgement
phases never downgrade), deterministic no-op skips, and unpriced-provider
handling where the INABILITY to enforce is loud (`enforceability:
enforced|partial|unenforceable` naming the missing `pricing:` key).

themselves, and it is the thing to preserve as more of them land.

## Suite wall-clock, measured (2026-08-09)

`python3 -m pytest registry/tests -q --durations=30`, run solo:
**2018 passed in 27:07**. Verdict on where that time goes:

| Cost | Where | Verdict |
|---|---|---|
| ~112s | `test_ticket_comment_idempotency` full mock retry run | INHERENT -- it drives the real pipeline twice |
| ~93s | `test_plan_first_journey` fixture **setup** | INHERENT -- it snapshots and restores the estate, which is what keeps it from feeding the scorecard its own traffic |
| 61s | `test_batch_provider::…never_ends…` | **ACCIDENTAL, fixed here** |
| ~45-59s each | ~12 tests that run `demo-pr` / `demo-jira` end to end | INHERENT |

The one accidental cost was mine, and it pointed at a real defect rather than
just a slow test. The deadline knob was parsed with `int()`, so the shortest
wait anyone could express was **60 seconds** -- and anything an operator might
reasonably write (`0.5`, `90s`, a stray quote) raised an **uncaught ValueError**
that surfaced as a Python traceback from inside an adapter, naming nothing.
`_num()` now parses a float, refuses non-numbers and non-positives with
`CONFIG_INVALID` naming the setting and exit 64, and the test asks for 0.05 min:
**61.4s -> 4.2s**, about 57 seconds off every full run.

**Parallelism is NOT the answer here, and the reason is recorded so it is not
re-proposed.** pytest-xdist is not installed, and installing it would not be
safe: these tests share one estate -- the registry, run records, the catalog --
which is exactly what made a concurrent `make review` + `make test-routing`
fail `test_architecture_current_estate_marker_matches_the_registry` today. Real
parallelism needs per-worker estate isolation first; that is a bigger change
than the 27 minutes currently justifies.

So the remaining 26 minutes are the price of end-to-end tests that drive the
actual pipeline, which is the reason they catch what they catch. Recorded as a
measurement rather than a target.

## What the coverage number does and does not mean (measured 2026-08-10)

`make python-coverage` reports **71.0%** across `engine/lib` and `bin`
(2061 tests, 27:50). That figure is enforced by `make python-coverage-check`
via `--cov-fail-under`, so it is worth knowing what it actually measures.

**It substantially understates real coverage**, because coverage.py only
instruments the process it starts, and much of this platform is deliberately
driven as SUBPROCESSES — `pipeline.sh` calls `run_record.py`, tests invoke
`bin/repos.py` and `bin/qa.py` as commands, the servers are started as child
processes. Three files therefore report **0.0%**:

| File | Coverage | Reality |
|---|---|---|
| `run_record.py` | 0.0% (156 stmts) | referenced by 30 test files, invoked as a subprocess by 17; **never imported in-process** |
| `gen_agents_md.py` | 0.0% (159) | 7 test files, all via subprocess |
| `repos.py` | 0.0% (164) | 56 test files reference it, 6 invoke it directly |
| `dashboard_server.py` | 9.5% (998) | tested by starting the real server |

None of those are untested. `run_record.py` in particular is covered by the
run-record write ordering pins and by every mock pipeline run in the suite.

**Why this matters more than a cosmetic inaccuracy.** A threshold on a number
that structurally cannot see subprocess execution rewards the wrong work:
writing thin in-process tests to move the figure, or lowering the bar when a
legitimately subprocess-driven module drags it down. Neither improves the
product.

**The fix, when it is worth doing:** coverage.py supports child processes via
`COVERAGE_PROCESS_START` plus a `sitecustomize` hook, which would fold
subprocess execution into the same report. Deferred rather than done here
because it changes how every test runs, the suite is already ~28 minutes, and
the change needs its own validation — measuring wrongly in a new direction is
not an improvement. **Trigger:** do it before anyone raises `--cov-fail-under`,
or the first time someone proposes deleting a subprocess-driven test because
"it shows 0% anyway".

Until then, read 71.0% as a FLOOR, and use the per-file numbers only for
modules the tests import directly.
