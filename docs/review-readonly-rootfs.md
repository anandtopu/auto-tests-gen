# R12 — writable-path audit for `readOnlyRootFilesystem`

Audit date: 2026-08-01. Method: a full-filesystem mtime snapshot across the
checkout before and after `make demo-pr` + `make demo-jira` (2331 → 2394 files,
68 created or modified), unioned with a static scan of every write site in
`engine/`, `bin/` and `catalog/`, then checked against a real container run.

The empirical half matters because the filed requirement listed the writable set
from memory and got it wrong in both directions.

## What R12 said, and what is actually true

R12 named five paths — `catalog/`, `testplans/`, `testdata/`, `specs/` and
`knowledge/generated/` — and prescribed "mount or relocate" them. Three things
are missing from that list and one thing in it is misleading.

**Missing 1 — `/tmp`.** `readOnlyRootFilesystem` makes the *whole* root
read-only, not just `/app`. Four SCM adapters and the CI-results receiver call
`mktemp`/`tempfile`:

| caller | use |
|---|---|
| `adapters/scm/github.sh` | `fetch_file` error capture |
| `adapters/scm/bitbucket.sh` | response body |
| `adapters/scm/stash.sh` | response body |
| `bin/with-env.sh` | compose-mode env log |
| `bin/taskevent_receiver.py` | JUnit XML upload staging |

R12 only looked inside `/app`, so this would have surfaced as adapters failing
in production after the flag shipped green in a demo.

**Missing 2 — Python bytecode.** The image sets no `PYTHONDONTWRITEBYTECODE`,
so CPython writes `__pycache__/` next to every module it imports — inside
`/app`. This is silent today (the write simply succeeds) and becomes a
first-import failure surface under a read-only root.

**Missing 3 — two root-level files.** `AGENTS.md` is regenerated by every
pipeline run, onboarding, bootstrap and mapping edit; `.env` is written by the
Settings UI. Neither is in a directory that can take a volume mount.

**Misleading — `catalog/` is not a writable directory.** It is a *mixed*
directory, and so is almost every other one on the list. That distinction is
what makes R12's prescribed fix wrong.

## Why "mount the writable paths" does not work

Every mutable directory except `testplans/` and `testdata/` holds code or
configuration alongside its data:

| directory | ships in the image (must upgrade) | mutates at runtime |
|---|---|---|
| `catalog/` | `bootstrap/*.py`, `schema.json`, `templates/` | `*.jsonl`, `review/`, `health.json` |
| `registry/` | `tests/`, `org-config.yaml` | `repo-registry.yaml` |
| `specs/` | `platform/constitution.yaml` | `<KEY>/` |
| `knowledge/` | `repos/`, `curated/`, `facts/*.yaml` (tracked) | `generated/`, `synced/`, `facts/derived/` |
| `.agents/skills/` | 7 hand-authored task skills | 2 generated convention skills |
| `testplans/`, `testdata/` | — | everything |

Mounting an empty volume over `catalog/` hides `catalog/bootstrap/*.py` and the
bootstrap stops existing. Seeding that volume from the image instead fixes the
first boot and breaks every one after it: the volume now owns `bootstrap/*.py`
and `org-config.yaml`, so an image upgrade ships new logic and new configuration
that never run. **That failure is silent** — the container is healthy, the
version label is new, and the behaviour is the old one. It is a worse bug than
the one being fixed, and it is the reason this audit changes the approach rather
than just listing mounts.

## The approach: relocate, don't mount over

`engine/lib/app_paths.py` resolves every mutable path as

```
the path's own env knob  →  AIQE_STATE_DIR/<relative path>  →  ROOT/<relative path>
```

With neither env var set, every function returns exactly the path callers
hard-coded before, so development and the demo estate are untouched — that is
the first pin in `test_app_paths.py`, and it is the one that matters most,
because a resolver that quietly moved a directory would relocate somebody's
plans on upgrade.

The per-path knobs (`AIQE_SPEC_DIR`, `AIQE_TESTPLAN_DIR`, `AIQE_SYNC_DIR`,
`AIQE_GENERATED_GUIDANCE_DIR`, `AIQE_HEALTH_FILE`, `AIQE_PLAN_DIR`,
`AIQE_QUEUE_FILE`, `AIQE_REVIEWS_FILE`, `AIQE_OPENHANDS_DIR`, `AIQE_DRIFT_FILE`,
`AIQE_ENV_FILE`, `AIQE_PHASE_CACHE_DIR`) already existed as the test-isolation
mechanism. They keep outranking `AIQE_STATE_DIR` so a test that redirects one
directory is unaffected by a container that redirects all of them.

Code and configuration are deliberately NOT resolvable through this module —
`org-config.yaml`, `catalog/bootstrap/`, `schema.json` and the hand-authored
skills travel with the image. A pin asserts no resolver ever points at them.

Seeding: `catalog`, `registry/repo-registry.yaml` and `knowledge` ship content
and must be copied into an empty state root on first boot. `AGENTS.md`,
`testplans/`, `testdata/` and `specs/<KEY>/` are purely generated — an empty
directory is their correct initial state, and seeding them from the image would
restore a stale plan over an empty volume and call it state.

## Confirmed against a real container

The image was built and run with `podman run --read-only`, probing every audited
path. **15 of 19 blocked**, matching the static audit exactly — no path was
missed and none was over-claimed:

```
BLOCKED   AGENTS.md  .env  .agents/skills/  catalog/*.jsonl  catalog/review/
          catalog/health.json  registry/repo-registry.yaml  specs/<KEY>/
          testplans/  testdata/  knowledge/{generated,synced,curated,facts/derived}
          engine/lib/__pycache__/
WRITABLE  reports/  out/  workspace/   (mounted)      /tmp  (see below)
```

Running the JIRA demo confirmed the order of failure: `AGENTS.md` first, then
`testplans/`. `AGENTS.md` is the proof that mounting cannot solve this — it is a
file at the checkout root, and there is no directory to mount over it.

**Two findings only the container run produced.**

*`/tmp` shows as writable here, and that is a trap.* `podman --read-only` mounts
a `/tmp` tmpfs automatically; Kubernetes does not. Verifying this work with
podman alone would pass locally and fail in the cluster. The manifests now mount
`/tmp` explicitly, before the flag is ever set.

*A read-only root was reported as lock contention.* `engine/pipeline.sh` takes
its run lock with `mkdir "$LOCK" 2>/dev/null`, which cannot distinguish `EEXIST`
("another run holds it") from `EROFS` ("nothing here is writable") — stderr is
discarded and both simply fail. The first read-only run therefore spun the full
120-second retry loop and printed `PIPELINE_BUSY: another run holds
out/.pipeline.lock`, sending an operator to hunt a concurrent run that does not
exist. This is the same defect class as review C3 (a Windows PENDING-DELETE lock
raising `PermissionError` where the code expected `FileExistsError`): a
distinguishable failure reported as the wrong one. Fixed with an up-front
writability check — the diagnosis is now `PIPELINE_UNWRITABLE`, it names the
directory, it says explicitly that this is *not* contention, and it returns in
0.08s instead of 120s. Genuine contention still reports `PIPELINE_BUSY`.

One limitation, stated rather than hidden: the check is `[ -w ]`, and for a
process running as **root** that can report writable on a read-only mount. The
platform runs as UID 1001 with `runAsNonRoot: true`, so this does not arise in
the supported configuration — and where it did, the behaviour would simply fall
back to today's 120-second `PIPELINE_BUSY`, which is no worse than before.

## One trap worth recording

`engine/gate/gate.sh` references `catalog/` too — but the gate runs *inside the
test repo checkout*, where `catalog/` is that repo's born-mapped sidecar, not
`/app/catalog`. Rewiring it to the state root would break the born-mapped check
(constitution C3) while looking like a consistent search-and-replace. The same
caution applies to `mock_phase.sh`, which writes both platform paths and
workspace paths.

## Status

**DONE.** `readOnlyRootFilesystem: true` is set on both containers and proven by
running the image with `podman run --read-only` against an EMPTY state volume:
the entrypoint seeded 8 data paths, `ensure_dirs` created the four generated
ones, `jira PROJ-301` and `pr orders-api#201` both reached `GATE_STATUS=COMMITTED`,
`touch /app/PROOF` was refused by the kernel, and a second start reported
"already populated — nothing seeded" rather than clobbering the volume.

### What the first EXECUTION of the entrypoint found (later pass)

The verification above ran the image; nothing ever ran the entrypoint *as a unit*
against a controlled state root, and `bin/container-entrypoint.sh` turned out to
be the only entry point in the repo that nothing referenced — no test, not the
Makefile, only the Dockerfile's `ENTRYPOINT`. The first such run seeded **zero**
files into an empty state root and printed *"state root already populated —
nothing seeded"* about a directory it had just created. Three causes:

* `< <(python3 … --seeded)` discards the producer's exit status, so a crashing
  `app_paths` was indistinguishable from "there is nothing to seed". It is a
  command substitution now, and failure is fatal — booting bare is worse than
  not booting, because a bare deployment routes nothing and looks healthy.
* python emits CRLF on some hosts, so `$ROOT/catalog/*.jsonl<CR>` matched no
  file and every path was skipped while the boot still claimed success.
* "we copied nothing" and "the volume already had it" shared one branch. The
  state root's pre-existing content is now sampled *before* seeding, so an empty
  root that received nothing warns instead of reporting a normal boot (C13).

And the seeding loop expanded globs and copied whole **directories** in bash, so
`catalog/review` carried `export_review_queue.py` plus its `__pycache__`, and
`knowledge/facts` carried the gitignored `derived/` tier — the very code-freeze
this document argues against, one level further down, with the pin on the other
side of the boundary asserting only that the `SEEDED` *strings* looked right.
`state_bundle` had already paid for this exact file once. Expansion and
exclusion now live in `app_paths.seed_plan()`; the entrypoint copies what it is
handed and decides nothing. `tests/entrypoint-smoke.sh` (17 checks, in
`make review`) pins all of it.

Two defects were found while wiring the seed step, both by pins rather than by
reading the code:

* `SEEDED` was directory-level, so seeding `catalog/` would have copied
  `bootstrap/*.py` into the volume — the code-freeze described above,
  reintroduced one level down. It is now data-only and narrower than the
  directories that contain it.
* `resolve_rel` relocated everything under a mutable directory, so
  `catalog/bootstrap/correlate.py` and `specs/platform/constitution.yaml`
  resolved into the state volume. `_FROZEN_SUBPATHS` now holds them in the
  image, matched by path SEGMENT — `startswith` would have caught a sibling
  `catalog/bootstrap-old/` too, which is R5's defect class.

Also rewritten: the pin guarding this. It used to scan the module source for
strings like "bootstrap" and broke the moment a comment explaining the exclusion
was added. A pin that fails on prose while the code is correct teaches people to
delete pins; it now asserts behaviour instead.
