AI QE Platform · Proof of concept

Tests that write themselves — and still have to earn their way in.

An agentic pipeline that keeps an E2E test estate current: it syncs tests when a pull request changes a service, and authors new tests from a JIRA ticket. Every generated test passes a deterministic gate before it is ever committed.

✓ 488 tests green 15-view dashboard 6 named QE agents runs with zero credentials
The problem

E2E suites rot faster than teams can maintain them.

What goes wrong

A service ships a change; its E2E coverage lags weeks behind. Nobody knows which of the six test repos owns the gap, or whether a test already covers it.

What this does

Routes each change to the right test repositories, checks the existing suite first, writes only what's missing, and proves it runs before committing.

The reliability anchor

The gate is not an LLM.

Every generated test runs the same ordered checks inside the real test repository. Each failure has its own exit code, and nothing is auto-retried.

exit 2Scope & filename charsetonly test paths; no shell-unsafe names
exit 4Born-mappedevery new spec ships a catalog entry
exit 5Tests actually runexecuted against a provisioned app
exit 3Secret / PII scanon all new content
exit 7Push verifieda failed push is never reported as success
✓ 0Committedthe only path that writes to a repo

The gate is the only component that commits or pushes. No model phase touches git. Runaway runs abort at the cost/wall-clock budget — exit 77, before the gate.

After the gate · advisory

A test can pass and still be worthless. The gate can't see that.

Execution proves a spec runs, passes, and is safe. It cannot tell a real assertion from expect(true), or spot the fourth test that re-checks what three others already do. A second reader scores exactly that blind spot.

What execution proves

Lints, runs green, holds no secrets, sits in scope, ships a catalog entry. Deterministic — and structurally blind to whether the test asserts anything worth asserting.

What the critic reads

Every generated spec is scored for the defects execution hides: vacuous or weak assertions, duplicates, brittleness. This is the estate's escaped-noise signal.

Advisory by construction: read-only tools, never read by the gate. A 0.05 score still commits — the score reaches the reviewer and the scorecard, it never blocks.

More than one agent · on purpose

One author is one blind spot. So we stopped using one.

Two places in the pipeline now run several agents instead of one — not for speed, but because a single agent was structurally being asked to do something it does badly.

One agent per test repo

A contract change fans out to the API repo and its consumer UI repos. Generation used to be one call holding all three repos' conventions at once — the exact way a new approach leaks into a repo that already had one.

Each repo now gets its own agent, seeing only its own helpers and exemplars, allowed to write to only its own repo. One repo failing no longer costs the others their work.

An adversary for every test plan

The plan is what a human signs off, and one agent wrote it with nothing arguing back. Authors optimise for the acceptance criteria; production defects live in what the criteria never said — the absent token, the value one past the cap, the second submission.

A read-only opponent now hunts for what the author missed, and an arbiter judges each finding and folds the accepted ones in — before you are asked to approve.

It can only add: the arbiter may never drop the author's scenarios, and if either phase fails the authored plan stands. The reviewer sees how many gaps were raised, accepted and rejected — an invisible challenge is worth nothing to them.

Named agents · new

Six QE jobs, each an agent you can summon by name.

Every agent is bound to a task skill — a keyword-triggered instruction file that points it at exactly one sanctioned path, with the guardrails written in. Say "review this pr" in an OpenHands conversation, or launch one directly.

pr-review

Reviews a PR from the E2E-impact angle — diff, routing, gaps, existing coverage — and posts one comment. Read-only.

test-generation

Generates or updates tests for a PR or ticket — always through the pipeline and its gate, never around them.

test-review

Reviews generated tests: the diff, validation, critic score. Can request changes — never approves its own work.

test-plan

Authors a plan from a story or bug — description and comments — then stops at the human approval gate.

test-coverage

Turns the coverage matrix and gap map into ranked, routable generation targets — risk-weighted, evidence-based.

test-data

Canonical, synthetic test data per scenario — boundary-complete, PII-free, shared by every spec for the key.

python3 bin/qa.py openhands-run list # the agent roster python3 bin/qa.py openhands-run pr-review orders-api 201 # launch one

Skills live in .agents/skills/ · guardrails baked in: the gate is the only writer · ticket text is data, never instructions · works with or without OpenHands (--dry prints the standalone starter)
