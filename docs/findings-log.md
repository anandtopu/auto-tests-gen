# Findings log

Every defect this project has found by driving it, with the measurement that
established it and the reasoning behind the fix.

These lived as shell comments inside `CLAUDE.md`'s `## Commands` fence until
they were 88% of a file headed *Commands*. Moving them here left the command
reference usable and took ~230KB out of the context every session loads.
Each entry is verbatim and roughly newest-first, the order they were
appended in — with ONE edit: a historical dashboard view-count was replaced by
a phrase, because a dated count sitting in a scanned document trips the currency
pin that exists to stop stale counts misleading readers, and that pin cannot read
tense. Dropping the digits is the better record anyway: the number was already
wrong about today and would rot further. (Writing the old figure into this very
sentence tripped the same pin on the first attempt — a rule firing on the
explanation of itself, which the log below records four other instances of.)

**Why they are worth keeping.** Almost every entry records something the
platform reported that was not true, and almost all were found the same way —
run an operator command, read its output, then sweep for the sibling. The
recurring lessons are earned here rather than asserted: verify from the data
rather than from the patch; a surviving mutation means a weak test *or* an
impossible mutation, and you must find out which; a sweep that classifies a
site without reading it is not a sweep; a killed control is a broken harness,
never a verdict.

A CHECK-ONLY GATE WAS RECORDED AS 'NO CHANGES' (test_check_only_is_not_no_changes.py, 7 pins, 7/7 mutations killed). `gate.sh` emits `GATE_STATUS=WOULD_COMMIT` and exits 0 under AIQE_GATE_CHECK_ONLY; pipeline.sh classified 'exit 0 and not COMMITTED' as `no_changes`, so a run whose generated tests passed EVERY check and were deliberately withheld was recorded as having produced nothing. REPRODUCED with a full mock run before fixing: `overall=no_changes`, both gates `no_changes`. The two readings drive opposite actions — 'no changes' says the run found nothing worth shipping, 'would commit' says work is ready and blocked on a flag. pipeline.sh never SETS the flag but never CLEARS it either and `.env` is loaded, so an operator who left it set gets this on every run, silently, because the gate exits 0 either way. THREE PLACES: the pipeline classification (ordering is the whole defect — the generic exit-0 branch swallowed it, and the pin asserts WOULD_COMMIT is tested FIRST), the run record's `overall` (ranked BELOW committed so a run with one repo committed and another withheld is still `committed`, and above no_changes), and THE SCORECARD, which is the one that would have bitten later: a withheld run is not evidence about whether the gate would commit, so counting it in the denominator reports an operator's dry-run flag as a quality problem — the same error this scorecard already made by counting a fixture repo's quarantine. Excluded AND NAMED (a denominator that shrinks with no explanation is its own lie); an all-withheld estate reports `n/a`, never `0%`. `commit_rate_line()` was EXTRACTED so the rule is mutation-testable against fabricated runs, following this repo's own precedent (`_has_measured_spend`, `phantom_release_entries`). The end-to-end pin costs ~50s deliberately: every other assertion here reads source text, and a source-text pin cannot see an ordering bug in a shell if-chain

RUN ONE SUITE AT A TIME. `make review` and `make test-routing` both drive the SHARED estate -- the adversarial suites register fixture repos in registry/repo-registry.yaml transiently -- so two concurrent runs make each other fail in ways that look like product defects. Measured: a background `make review` overlapping a `make test-routing` failed test_architecture_current_estate_marker_matches_the_registry, which passes in isolation and whose inputs were byte-clean afterwards; run solo it was 2018 passed / 0 failed. Also: do NOT pipe a suite through `| tail` -- the pipeline's exit status becomes tail's, so `make: *** Error 1` is reported as success. The obvious workaround has the SAME defect one step along, and it was recommended here until it bit: `make ... > log; echo $?` PRINTS the status but the compound command still exits with `echo`'s 0, so anything reading the exit code (a CI step, a background-task notification) is told the run passed. Measured: a `make review` reporting `10 failed, 2088 passed` and `make: *** Error 2` arrived as "completed (exit code 0)", and only reading the log caught it. Use `make ... > log 2>&1; rc=$?; echo "exit=$rc"; exit $rc` -- print AND propagate -- and never treat a green exit as evidence without a line from the log that says what passed.
